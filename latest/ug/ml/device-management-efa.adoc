[#device-management-efa]
= Manage EFA devices on Amazon EKS
:info_titleabbrev: EFA devices

[abstract]
--
Learn how to manage Elastic Fabric Adapter (EFA) devices in Amazon EKS clusters using the EFA DRA driver (DRANET) or device plugin for high-performance inter-node communication.
--

link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html[Elastic Fabric Adapter] (EFA) is a network device for Amazon EC2 instances that enables high-performance inter-node communication and RDMA (Remote Direct Memory Access) for artificial intelligence, machine learning, and High Performance Computing (HPC) workloads. Amazon EKS supports two mechanisms for managing EFA devices in EKS clusters: the _EFA Dynamic Resource Allocation (DRA) driver (DRANET)_ and the _EFA device plugin_.

[#eks-efa-dra-vs-device-plugin]
== EFA DRA driver vs. EFA device plugin

[cols="1,2,2", options="header"]
|===
| Feature
| EFA DRA driver
| EFA device plugin

| Minimum Kubernetes version
| 1.34
| All EKS-supported Kubernetes versions

| EKS Compute
| EKS Auto Mode (Kubernetes 1.36 and later), Karpenter, managed node groups, self-managed nodes
| EKS Auto Mode, Karpenter, managed node groups, self-managed nodes

| EKS-optimized AMIs
| AL2023, Bottlerocket
| AL2023, Bottlerocket

| Device advertisement
| Rich attributes via `ResourceSlice` objects including device type, topology, and PCIe locality
| Integer count of `vpc.amazonaws.com/efa` extended resources

| GPU-EFA affinity
| DRA-native topology-awareness
| Automatic topology-awareness (EKS-optimized AL2023 AMIs only)

| Neuron-EFA affinity
| DRA-native topology-awareness
| Automatic topology-awareness (EKS-optimized AL2023 AMIs only)

| Device sharing
| Not supported. Each EFA device is exclusively allocated to one Pod. For more information, see <<efa-dra-share>>.
| Not supported. Each EFA device is exclusively allocated to one Pod.

|===

We recommend using DRA drivers for new deployments with Kubernetes versions 1.34 and later. With the EFA DRA driver, you can configure topology-aware allocation that pairs EFA interfaces with their topologically-local GPUs or Neuron devices.

EKS Auto Mode includes the EFA DRA driver in the node runtime on Kubernetes version 1.36 and later, so you do not install or manage it. For more information, see <<dra-auto-mode>>. With Karpenter, EKS managed node groups, or self-managed nodes, you install the EFA DRA driver yourself. Karpenter supports DRA with both dynamic and static capacity provisioning as of Karpenter version 1.15. Dynamic provisioning requires enabling Karpenter feature gates. For more information, see <<dra-karpenter>>.

With EFA, High Performance Computing (HPC) applications using the Message Passing Interface (MPI) and machine learning applications using the NVIDIA Collective Communications Library (NCCL) can scale to thousands of CPUs or GPUs, which gives you the application performance of an on-premises HPC cluster with the elasticity of the {aws} Cloud. Using EFA with Pods running on Amazon EKS can reduce the time to complete large-scale distributed training workloads without adding instances to your cluster. For more information about EFA, see link:hpc/efa/[Elastic Fabric Adapter,type="marketing"].

[#eks-efa-interfaces]
== EFA and EFA-only interfaces

An _Elastic Fabric Adapter (EFA)_ is a network interface that combines the capabilities of an Elastic Network Adapter (ENA) and an OS-bypass interface, powered by the {aws} Scalable Reliable Datagram (SRD) protocol. The OS-bypass interface lets applications communicate directly with the hardware for low-latency transport, while the ENA capabilities carry normal IP traffic.

Amazon EC2 offers two interface types for EFA:

* *`efa`*: Provides both the ENA and OS-bypass capabilities on one interface. The interface receives an IP address from your subnet.
* *`efa-only`*: Provides only the OS-bypass capability. The interface does not receive an IP address and communication is limited to interfaces within the same Availability Zone.

*We recommend `efa-only` interfaces for all interfaces except the primary network interface.* Distributed training and HPC traffic uses the OS-bypass path, not the IP path, so the IP addresses that `efa` interfaces consume go unused. On an instance such as `p5.48xlarge` or `p6-b200.48xlarge` with dozens of network interfaces, those unused addresses can exhaust a subnet's available IP space. For more information, see <<eks-efa-conserve-ip>>.

Note the following requirements for `efa-only` interfaces:

* You cannot set network card `0` to `efa-only`, because it is the primary network card and network interface of the instance. Configure network card `0`, device index `0` as `interface` and use `efa-only` for the remaining interfaces.
* Amazon VPC CNI version `1.18.5` or later is required. For more information about updating the VPC CNI, see <<managing-vpc-cni>>.
* You cannot use `eksctl`'s `efaEnabled` setting to create nodes with `efa-only` interfaces, because `efaEnabled` configures every interface as type `efa`. Use a `NodeClass`, an `EC2NodeClass`, or a launch template instead, as shown in the examples that follow.

[#eks-efa-instance-types]
== Choosing an EFA-enabled instance type

EFA is supported on a specific set of Amazon EC2 instance types. For the full list, see link:AWSEC2/latest/UserGuide/efa.html#efa-instance-types[Supported instance types,type="documentation"] in the _Amazon EC2 User Guide_. To run machine learning workloads, we recommend an instance type that also has hardware acceleration chips such as NVIDIA GPUs or link:machine-learning/trainium/[{aws} Trainium,type="marketing"] chips. For the list of instance types that have both accelerators and EFA, see link:AWSEC2/latest/UserGuide/efa.html#efa-instance-types[Accelerated computing,type="documentation"] in the _Amazon EC2 User Guide_.

As you compare instance types, consider the number of EFA network cards available alongside the number of accelerator cards, vCPUs, and memory. You can assign up to one EFA per network card, and an EFA counts as a network interface. To see how many EFAs each instance type supports, see the link:AWSEC2/latest/UserGuide/using-eni.html#network-cards[Network cards,type="documentation"] list in the _Amazon EC2 User Guide_. For the recommended interface layout to reach maximum network bandwidth on each instance type, see link:AWSEC2/latest/UserGuide/efa-acc-inst-types.html[Maximize network bandwidth for EFA-enabled instance types,type="documentation"] in the _Amazon EC2 User Guide_.

To find which EFA-enabled instance types are available in an {aws} Region, and which Availability Zones offer them, run the following commands. Replace [.replaceable]`region-code` with your {aws} Region.

[source,bash,subs="verbatim,attributes"]
----
aws ec2 describe-instance-types --region [.replaceable]`region-code` \
    --filters Name=network-info.efa-supported,Values=true \
    --query "InstanceTypes[*].[InstanceType]" --output text
----

[source,bash,subs="verbatim,attributes"]
----
aws ec2 describe-instance-type-offerings --region [.replaceable]`region-code` \
    --location-type availability-zone \
    --filters Name=instance-type,Values=[.replaceable]`p5.48xlarge` \
    --query 'InstanceTypeOfferings[*].Location' --output text
----

An example output is as follows.

[source,bash,subs="verbatim,attributes"]
----
us-west-2a    us-west-2c    us-west-2b
----

Your VPC must have subnets with available IP addresses in one of the Availability Zones returned. Because `efa-only` interfaces communicate only within an Availability Zone, place the nodes of a single distributed job in one Availability Zone.

[IMPORTANT]
.EFA requires hugepages
====
EFA requires hugepages. The EFA installer, which is included in the EKS-optimized AL2023 accelerated AMIs and the Bottlerocket AMIs, reserves 2 MiB hugepages when a node boots. You request them as `hugepages-2Mi` resources in your workload specifications, and the examples in this topic request hugepages alongside EFA devices.

Note the following about this reservation:

* *It requires an EFA device, not just the EFA software.* The reservation runs only on instances that have an EFA device attached. An accelerated node that has the EFA installer but no EFA interface reserves no hugepages, and a Pod that requests `hugepages-2Mi` on such a node stays in the `Pending` state.
* *The amount scales with the size of the instance.* The reservation covers the packet pools that the libfabric EFA provider creates for each endpoint, so it grows with the number of vCPUs. A `c5n.18xlarge` reserves roughly 15 GiB and a `p5.48xlarge` roughly 41 GiB. Do not assume a fixed amount.
* *It only ever increases the reservation.* If a node already has more 2 MiB hugepages reserved, for example from node user data, the EFA installer leaves that reservation in place.

To see what a node actually reserved, check its capacity:

[source,bash,subs="verbatim,attributes"]
----
kubectl get nodes -o custom-columns='NAME:.metadata.name,2Mi:.status.capacity.hugepages-2Mi'
----

Size your Pod requests against what your nodes report, rather than against a fixed figure. For more information about configuring hugepages on EKS nodes, see <<ml-hugepages>>, and for the Kubernetes resource model, see https://kubernetes.io/docs/tasks/manage-hugepages/scheduling-hugepages/[Manage HugePages] in the Kubernetes documentation.
====

[#eks-efa-nodes]
== Creating EKS nodes with EFA interfaces

When you create EKS nodes with EFA interfaces, the EFA interfaces are attached to the instance during instance provisioning. You can customize the per-device EFA configuration and use link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/placement-groups.html[placement groups] with EKS Auto Mode, Karpenter, EKS managed node groups, or EKS self-managed node groups. With EKS Auto Mode, you pass configuration for each network interface through the `NodeClass` under `advancedNetworking.networkInterfaces`. With Karpenter, you pass configuration for each network interface via the `EC2NodeClass`. With EKS managed node groups or self-managed nodes, you pass configuration for each network interface with link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-launch-templates.html[launch templates].

When using <<eksctl-install-update, `eksctl`>> for provisioning EKS nodes with the `efaEnabled` setting, all interfaces are configured with interface type `EFA`, an EFA-specific security group is created, and the EFA device plugin is installed on the cluster. If you need to customize the per-device EFA configuration when using `eksctl`, it is recommended to use `eksctl`'s support for link:https://docs.aws.amazon.com/eks/latest/eksctl/launch-template-support.html[launch templates].

The following examples show how to configure `NodeClass` and launch templates with EFA interfaces. This is useful to customize the interfaces used for EFA vs standard IP-based traffic. For information on the number of EFA interfaces supported by each instance type and how to configure them for maximum network bandwidth, see link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-acc-inst-types.html[Maximize network bandwidth for EFA-enabled instance types,type="documentation"] in the _Amazon EC2 User Guide_.

[IMPORTANT]
.Dynamic capacity provisioning assumes all EFA interfaces are attached
====
When EKS Auto Mode or Karpenter uses dynamic capacity provisioning to launch a node for an EFA DRA claim, it chooses the instance type before the node exists, by evaluating the claim against device metadata for each candidate instance type. That metadata assumes the node is configured with an EFA interface on every EFA-capable network card the instance type supports, and it is what PCIe alignment constraints are evaluated against.

If a node is launched with fewer EFA interfaces than its instance type supports, EKS Auto Mode and Karpenter overestimate the EFA devices the node will offer, and can launch a node that cannot satisfy the claim. For EFA DRA workloads that use dynamic capacity provisioning, leave the network interface configuration unset and let EKS Auto Mode or Karpenter attach an EFA interface on every EFA-capable network card for you.

Note the following about the device metadata:

* *It covers instance types with NVIDIA GPUs.* EKS Auto Mode and Karpenter don't yet have EFA DRA device metadata for EFA-enabled instance types without GPUs, such as `hpc7a` or `c6in`. As a result, dynamic capacity provisioning can't launch them for an EFA DRA claim. Support for these instance types is coming soon. For more information, see https://github.com/aws/karpenter-provider-aws/pull/9879[aws/karpenter-provider-aws#9879] on GitHub. Until then, use static capacity provisioning, EKS managed node groups, self-managed nodes, or the EFA device plugin for them.

This assumption does not apply to static capacity provisioning, EKS managed node groups, or self-managed nodes. On those, the nodes exist before any claim is evaluated and the EFA DRA driver publishes `ResourceSlice` objects for the interfaces that are actually attached.
====

[#eks-efa-auto-mode]
== EKS Auto Mode

In EKS Auto Mode, you configure EFA network interfaces using the `advancedNetworking.networkInterfaces` field in the `NodeClass` (`eks.amazonaws.com/v1`). Each entry specifies a `networkCardIndex`, `deviceIndex`, and `interfaceType`. The `interfaceType` can be `interface` for standard network interfaces or `efa-only` for EFA interfaces dedicated to RDMA traffic without IP addresses assigned.

When `networkInterfaces` is configured, instances launched by the `NodePool` referencing the `NodeClass` use this configuration regardless of whether Pods request `vpc.amazonaws.com/efa` resources. EKS Auto Mode does not attach additional IPs, prefixes, or ENIs after instance launch for nodes with static network interface configuration — only the interfaces and IPs configured at launch are available to Pods.

This feature can be used with <<auto-static-capacity,static capacity node pools>> to maintain pre-warmed, EFA-ready nodes for distributed training and inference workloads.

[IMPORTANT]
.EFA nodes need a subnet with a route to the internet
====
Run EFA workloads on private subnets with a NAT gateway, or on subnets with the {aws} PrivateLink endpoints your workloads need. Do not rely on a public subnet that assigns public IP addresses.

Amazon EC2 does not assign a public IP address to an instance whose launch specifies more than one network interface. An EFA-enabled node is launched with several interfaces, whether EKS Auto Mode attaches them for you or you configure more than one entry in `advancedNetworking.networkInterfaces`. Such a node receives no public IP address, even in a subnet that has `MapPublicIpOnLaunch` enabled. The node still joins the cluster over the Amazon EKS private endpoint, so it reports `Ready`, but it has no route to the internet. Image pulls then fail with a timeout and your Pods stay in the `ImagePullBackOff` or `ErrImagePull` state.

This applies to EFA workloads that use DRA and to EFA workloads that request the `vpc.amazonaws.com/efa` extended resource, because it depends only on how many network interfaces the node is launched with. It does not affect nodes that are launched with a single network interface, which do receive a public IP address.
====

[IMPORTANT]
.Combining a custom interface layout with topology-aligned allocation
====
Don't use dynamic capacity provisioning, static network interface configuration, and topology-aligned GPU and EFA allocation together. The behavior of this combination is undefined.

EKS Auto Mode still launches a node, but the Pod can then fail to schedule onto it and remain in the `Pending` state. You don't get an error when the node is provisioned. This happens because the device metadata that EKS Auto Mode evaluates the claim against assumes an EFA interface on every EFA-capable network card. An interface list that configures fewer than that makes EKS Auto Mode overestimate the topologically-aligned devices the node will offer.

Static network interface configuration is intended for static capacity provisioning. If you need a custom interface layout together with topology-aligned allocation, use <<auto-static-capacity,static capacity node pools>>. For more information, see <<dra-auto-mode>>.
====

When you do not configure `networkInterfaces` and a Pod claims EFA devices through DRA, EKS Auto Mode attaches the EFA interfaces for you. EKS Auto Mode includes the EFA DRA driver in the node runtime on Kubernetes version 1.36 and later, so you do not install the driver described in <<efa-dra-driver>>. You do need to create the EFA `DeviceClass` yourself, because EKS Auto Mode runs the driver from the node runtime rather than from the Helm chart that would otherwise create it. For the definition to apply, see <<dra-auto-mode-deviceclass>>.

The interfaces that EKS Auto Mode attaches for you are `efa` interfaces, so each one receives a private IP address from your subnet. Size your subnets for one private IP address per EFA-capable network card on every node you expect to launch this way.

To use the `efa-only` interfaces recommended in <<eks-efa-conserve-ip>> instead, configure `advancedNetworking.networkInterfaces` on the `NodeClass` and choose the interfaces attached at launch yourself, as described earlier in this section. The combination to avoid is dynamic capacity provisioning together with a custom interface list and topology-aligned GPU and EFA allocation.

You don't select DRA rather than the EFA device plugin for a `NodePool`. With dynamic capacity provisioning, EKS Auto Mode infers which of the two a node uses from the workloads it launches the node for. To pin every node a `NodePool` launches to one of them, which static capacity provisioning requires, set the `eks.amazonaws.com/device-manager-efa` label to `dra` or `device-plugin` on the `NodePool` template. For more information, see <<dra-auto-mode>>.

[#eks-amis-efa]
== Using EKS-optimized AMIs with EFA

The EKS-optimized AL2023 AMIs and all Bottlerocket AMIs include the host-level components required to use EFA, specifically the components installed by the link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-start.html#efa-start-enable[aws-efa-installer]. The EKS AL2023 and Bottlerocket AMIs **do not include** the EFA DRA driver or EFA device plugin, and these must be installed separately on your cluster before deploying workloads.

[#eks-efa-conserve-ip]
== Conserving IP address allocation

EFA-enabled instances such as `p5.48xlarge` and `p6-b200.48xlarge` support many network interfaces. By default, the Amazon VPC CNI allocates IP addresses across all IP-enabled attached ENIs, which can consume a large number of IP addresses from your subnet even when those addresses are not actively used by Pods. On instances with dozens of network interfaces, this can quickly exhaust your subnet's available IP space.

To reduce IP address consumption on EFA-enabled nodes, configure your network interfaces to use `efa-only` for all interfaces except the primary. EFA-only interfaces are dedicated to RDMA traffic and do not have IP addresses assigned, so they do not consume addresses from your subnet. For example configurations, see <<eks-efa-auto-karpenter>> and <<eks-efa-mng-self-managed>>. For the recommended interface layout for each instance type, see link:https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-acc-inst-types.html[Maximize network bandwidth for EFA-enabled instance types,type="documentation"] in the _Amazon EC2 User Guide_.

In addition to using `efa-only` interfaces, you can configure the Amazon VPC CNI to limit the number of warm (pre-allocated) IP addresses and ENIs. By default, the VPC CNI pre-allocates a warm pool of ENIs and IP addresses for faster Pod startup, but on large instances this can reserve hundreds of unused IP addresses. Set the `WARM_IP_TARGET` and `WARM_ENI_TARGET` environment variables on the `aws-node` DaemonSet to control how many spare IP addresses and ENIs the CNI maintains. For more information on these settings, see link:https://docs.aws.amazon.com/eks/latest/best-practices/vpc-cni.html#_overview[Amazon VPC CNI best practices,type="documentation"].

[NOTE]
====
The `WARM_ENI_TARGET` and `WARM_IP_TARGET` settings are cluster-wide and apply to all nodes managed by the VPC CNI. There is currently no way to set different values for each node group or instance type. If you need more granular control of these settings, provide feedback on link:https://github.com/aws/containers-roadmap/issues/1834[containers-roadmap issue #1834] on GitHub.
====

[#efa-dra-driver]
== Install the EFA DRA driver (DRANET)

The EFA DRA driver is built in the upstream link:https://github.com/kubernetes-sigs/dranet[DRANET] project on GitHub, which provides cloud-aware network device management for Kubernetes DRA. _EFA DRA driver_ and _DRANET_ are used interchangeably throughout this documentation and refer to the same tool. 

The EFA DRA driver advertises EFA devices as `ResourceSlice` objects with the driver name `dra.net` and the `DeviceClass` name `efa.networking.k8s.aws`. The EFA DRA driver runs as a DaemonSet on each node and automatically discovers EFA devices.

[NOTE]
.EKS Auto Mode includes this driver
====
Skip this section if you use EKS Auto Mode. EKS Auto Mode includes the EFA DRA driver in the node runtime on Kubernetes version 1.36 and later. You do need to create the `DeviceClass` object, as described in <<efa-dra-deviceclass>>. For more information, see <<dra-auto-mode>>.
====

=== Prerequisites

[#efa-dra-deviceclass]
== Create the EFA DeviceClass

A `DeviceClass` names a category of devices and defines the expression that selects them. Every `ResourceClaim` and `ResourceClaimTemplate` references one by name, so the EFA `DeviceClass` must exist before an EFA claim can be allocated. A claim that references a `DeviceClass` that does not exist is never allocated, and the Pod stays in the `Pending` state.

When you install the EFA DRA driver with Helm, as described in <<efa-dra-driver>>, the chart creates this object for you and there is nothing more to do. EKS Auto Mode runs the driver from the node runtime rather than from a Helm chart, so on EKS Auto Mode you create it yourself.

[source,bash,subs="verbatim,attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: efa.networking.k8s.aws
spec:
  selectors:
  - cel:
      expression: |
        device.driver == "dra.net" &&
        device.attributes["dra.net"].pciDevice == 'Elastic Fabric Adapter (EFA)'
EOF
----

The EFA DRA driver advertises every network interface on the node, not only EFA devices, so the selector filters to EFA devices. Without that filter, a claim could be allocated a network interface that is not an EFA device.

Confirm that it exists.

[source,bash,subs="verbatim,attributes"]
----
kubectl get deviceclass
----

An example output is as follows.

[source,bash,subs="verbatim,attributes"]
----
NAME                     AGE
efa.networking.k8s.aws   5s
----

This definition matches the one the driver's Helm chart installs, so the same claims work on EKS Auto Mode and on clusters where you manage the driver yourself. For more information about DRA on EKS Auto Mode, see <<dra-auto-mode>>.

[#efa-dra-topology-aware]
== Topology-aware EFA and GPU/Neuron device allocation

The EFA DRA driver supports topology-aware allocation that pairs EFA interfaces with GPUs or Neuron devices on the same PCIe root. Use the `matchAttribute` constraint to align EFA and GPU or Neuron device allocations. To use this capability, you must also use the NVIDIA or Neuron DRA drivers. For more information, see <<device-management-nvidia>> and <<device-management-neuron>>.

The following example requests 1 EFA interface aligned with 1 NVIDIA GPU:

[source,yaml,subs="verbatim,attributes"]
----
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: aligned-efa-nvidia
spec:
  spec:
    devices:
      requests:
      - name: 1-efa
        exactly:
          deviceClassName: efa.networking.k8s.aws
          count: 1
      - name: 1-gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          count: 1
      constraints:
      - requests: ["1-gpu", "1-efa"]
        matchAttribute: "resource.kubernetes.io/pcieRoot"
----

The following example requests 4 EFA interfaces aligned with 4 Neuron devices:

[source,yaml,subs="verbatim,attributes"]
----
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: aligned-efa-neuron
spec:
  spec:
    devices:
      requests:
      - name: 4-neurons
        exactly:
          deviceClassName: neuron.aws.com
          count: 4
      - name: 4-efas
        exactly:
          deviceClassName: efa.networking.k8s.aws
          count: 4
      constraints:
      - requests: ["4-neurons", "4-efas"]
        matchAttribute: "resource.aws.com/devicegroup4_id"
----

The number in the `devicegroup` attribute name corresponds to the number of Neuron devices in the connected topology group. For example, `resource.aws.com/devicegroup1_id` identifies a single Neuron device, `resource.aws.com/devicegroup4_id` identifies a group of 4 connected devices, and `resource.aws.com/devicegroup8_id` and `resource.aws.com/devicegroup16_id` identify groups of 8 and 16 connected devices respectively. Choose the `matchAttribute` that matches the device `count` in your request so that the allocated Neuron devices and EFA interfaces belong to the same connected topology group. For more information on these attributes, see the link:https://awsdocs-neuron.readthedocs-hosted.com/en/latest/containers/neuron-dra.html[Neuron DRA driver documentation].

You can use `allocationMode` to simplify how EFA devices are allocated to aligned GPU or Neuron accelerators. The `allocationMode` field supports two values: `ExactCount` (the default) requests a specific number of devices specified by `count`, and `All` requests all matching devices in a pool. For example, on `p5.48xlarge` instances there are four EFA devices that share the same PCIe root with one GPU. To allocate these groups of EFA devices with aligned GPUs, even if you do not know the exact EFA-GPU device mapping and count of aligned EFA devices, you can configure your `ResourceClaimTemplate` with `allocationMode: All` for the EFA devices.

[source,yaml,subs="verbatim,attributes"]
----
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: aligned-all-efa-one-nvidia
spec:
  spec:
    devices:
      requests:
      - name: all-efas
        exactly:
          deviceClassName: efa.networking.k8s.aws
          allocationMode: All
      - name: one-gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          allocationMode: ExactCount
          count: 1
      constraints:
      - requests: ["all-efas", "one-gpu"]
        matchAttribute: "resource.kubernetes.io/pcieRoot"
----

=== Request an aligned claim from a Pod

A `ResourceClaimTemplate` only describes the devices to allocate. To use it, reference it from your Pod specification. List the template under `resourceClaims` with a name that is local to the Pod, then reference that local name from each container's `resources.claims` so the container receives the allocated devices. Kubernetes generates a separate `ResourceClaim` for each Pod, so each Pod gets its own aligned set of EFA interfaces and GPUs.

The following example references the `aligned-efa-nvidia` template from the first example in this section, which allocates one EFA interface aligned with one NVIDIA GPU on the same PCIe root.

[source,yaml,subs="verbatim,attributes,quotes"]
----
apiVersion: v1
kind: Pod
metadata:
  name: training-worker
spec:
  containers:
  - name: worker
    image: [.replaceable]`my-training-image`
    resources:
      claims:
      - name: aligned-devices
      limits:
        hugepages-2Mi: 5120Mi
      requests:
        hugepages-2Mi: 5120Mi
  resourceClaims:
  - name: aligned-devices
    resourceClaimTemplateName: aligned-efa-nvidia
  tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
----

Note the following about this specification:

* *`resourceClaims`* names the template to use. The `name` field (`aligned-devices`) is an identifier local to this Pod, not the name of a cluster object. The `resourceClaimTemplateName` field is the name of the `ResourceClaimTemplate` object.
* *`resources.claims`* gives the container access to the devices from that claim. A container that omits this does not receive the devices, even though the Pod holds the claim. If a Pod has several containers, list the claim in each container that needs the devices.
* *`hugepages-2Mi`* is required because EFA transfers use hugepages. Adjust the amount to match your workload and the hugepages your nodes reserve, which depends on instance size. For more information, see <<eks-efa-instance-types>> and <<ml-hugepages>>.
* *The toleration* is needed only if your GPU nodes carry a taint such as `nvidia.com/gpu`. Adjust or remove it to match your `NodePool`.
* *No extended resources are requested.* Do not add `vpc.amazonaws.com/efa` or `nvidia.com/gpu` to `resources.limits`. Those are device plugin resources, and requesting them makes the Pod a device plugin Pod rather than a DRA Pod. For more information, see <<device-management>>.

To use one of the other templates in this section, change `resourceClaimTemplateName` to that template's name. For a Neuron-aligned claim, replace the GPU toleration with the taint your Neuron nodes use.

Give each Pod its own EFA devices. EFA devices cannot be shared between Pods. For more information, see <<efa-dra-share>>.

[#efa-dra-share]
== EFA device sharing between Pods is not supported

An EFA device is allocated to one Pod at a time. Unlike NVIDIA GPUs, which several Pods can share through a `ResourceClaim` that each of them references, EFA devices do not support this pattern. Use a `ResourceClaimTemplate`, which generates a separate claim and a separate set of devices for each Pod, as shown in <<efa-dra-topology-aware>>.

This is a property of the EFA DRA driver rather than a limitation of DRA. The driver prepares a claim for one Pod only, and rejects a claim that is reserved for more than one Pod before it attaches any device.

If you create a `ResourceClaim` and reference it from several Pods with `resourceClaimName`, Kubernetes allows the reference and schedules every Pod onto the node where the devices were allocated. The driver then fails to prepare the claim and the kubelet reports a `FailedPrepareDynamicResources` event with the message `driver only supports one pod per claim`. Every Pod that references the claim stays in the `ContainerCreating` state, and none of them receive the devices. If you then reduce the Pods that reference the claim to one, the remaining Pod starts on the next retry.

A `ResourceClaim` referenced by a single Pod is allocated and prepared normally. Use a `ResourceClaimTemplate` instead when each Pod needs its own devices, so that a second Pod cannot reference a claim that is already in use.

Processes that need to share one EFA device must run in the same Pod. The driver prepares the claim once for the Pod, so list the claim in each container's `resources.claims` and every container receives the same devices.

Sharing an RDMA device such as an EFA device between Pods is tracked upstream in link:https://github.com/kubernetes-sigs/dranet/issues/63[dranet issue 63].

== Install the EFA Kubernetes device plugin

The EFA Kubernetes device plugin advertises EFA devices as `vpc.amazonaws.com/efa` extended resources. You request EFA devices in container resource requests and limits.

[IMPORTANT]
====
Topology-aligned allocation of NVIDIA GPUs or Neuron devices with EFA interfaces happens automatically when using the EKS-optimized AL2023 accelerated AMIs. This automatic alignment does not occur when using Bottlerocket EKS-optimized AMIs or custom AMIs. If you need topology-aligned accelerator and EFA device allocation with Bottlerocket or custom AMIs, use the EFA DRA driver and the corresponding Neuron DRA driver. To use the NVIDIA DRA driver on Bottlerocket, you must first disable the NVIDIA device plugin that is bundled with the Bottlerocket NVIDIA variants, which requires Bottlerocket version 1.63.0 or later. [IMPORTANT]

If you are using EKS managed node groups or self-managed nodes with the NVIDIA device plugin, you must explicitly disable MOFED. For instructions, see <<eks-nvidia-device-plugin>>.

EKS Auto Mode does not enable MOFED by default and is not affected by this issue.

== Test EFA performance with NCCL tests

After you install either the EFA DRA driver or the EFA device plugin, we recommend validating the setup before you run production workloads. The https://github.com/NVIDIA/nccl-tests[NCCL tests] measure collective-communication performance across nodes and confirm that GPUDirect RDMA over EFA is working. You can also find packaged versions of these tests in the https://github.com/aws-samples/awsome-distributed-training/tree/main/micro-benchmarks/nccl-tests[awsome-distributed-training] repository on GitHub.

The following procedure runs a two-node `all_reduce_perf` benchmark on `p5.48xlarge` instances. ====

Hugepages remain an extended resource under DRA, so the worker still requests `hugepages-2Mi` directly. Only the EFA and GPU devices move to the `ResourceClaimTemplate`.
