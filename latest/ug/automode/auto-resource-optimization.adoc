[.topic]
[#auto-resource-optimization]
= Rightsize workloads with {ro-short}
:info_titleabbrev: Rightsize workloads

[abstract]
--
Use {ro-name} to set CPU and memory requests for workloads in EKS Auto Mode clusters based on observed usage.
--

[NOTE]
.Preview release
====
{ro-name} is in preview release for Amazon EKS and is subject to change.
====

{ro-name} is a capability of EKS Auto Mode. It recommends CPU and memory requests for your workloads based on the usage it observes for each container. For each workload, you choose whether {ro-short} only reports recommendations or also applies them to running Pods. For example, you can rightsize every application namespace without editing Pod templates or creating drift in your GitOps tools.

Teams usually set CPU and memory requests when they first deploy a workload and rarely revisit them. EKS Auto Mode provisions EC2 instances to fit those requests. When requests are higher than a workload needs, you run more or larger instances than the workload uses. With {ro-short}, requests follow what each workload actually uses.

[#auto-ro-how-it-works]
== How {ro-short} works

You turn on {ro-short} by creating a `ClusterResourceOptimizationPolicy` in your cluster. The policy selects which namespaces and workloads {ro-short} manages, and sets a mode for them:

`Recommend` (default)::
{ro-short-cap} collects usage and produces recommendations. It doesn't change any Pod.

`Apply`::
{ro-short-cap} also resizes running Pods to match its recommendations.

A policy that doesn't set `mode` uses `Recommend`. Creating a policy doesn't change any Pod until you set `mode: Apply`.

For each workload that a policy selects, {ro-short} creates a `ResourceOptimization` object (short name `ro`) in the workload's namespace. This object holds the workload's recommendations, its status, and the policy that supplied each setting. You don't create or edit these objects. {ro-short-cap} removes them when no policy selects the workload.

[#auto-ro-how-changes-apply]
=== How changes are applied

In `Apply` mode, {ro-short} resizes Pods in place through the Kubernetes Pod `resize` subresource, without recreating them. It never edits the Deployment or StatefulSet Pod template. The Pod template in your cluster matches the one in your source repository. GitOps tools such as Argo CD and Flux don't detect drift and have nothing to revert.

New Pods that the workload creates, for example during a scale-out, a node consolidation, or a rollout, start at the recommended size rather than the size in the Pod template. For exceptions, such as workloads with no requests or resources that a Horizontal Pod Autoscaler scales on, see <<auto-ro-workloads>>.

For more information about how {ro-short} handles resizes that don't fit on the current node, see <<auto-ro-resize>>.

[#auto-ro-profile]
=== How recommendations are sized

Recommendations follow an optimization profile. This preview includes one profile, `Balanced`:

* For CPU, {ro-short} sizes the request so that the 95th percentile of the container's observed usage is about 87% of the request.
* For memory, it sizes the request so that the 95th percentile of observed usage is about 70% of the request. Memory gets more headroom than CPU because a container that runs out of memory is stopped, while a container that runs short of CPU is only throttled.
* Recommendations stay within a band that's shared across the containers in a Pod: from half of the smallest request declared in the Pod template to twice the largest declared limit. If a container declares no limit, the band has no upper bound, and recommendations can grow to the largest size that your NodePools can fit. For details, see <<auto-ro-reference>> and <<auto-ro-workloads>>.

{ro-short-cap} needs about 12 hours of usage history for a container before it produces the first recommendation. Until then, the container keeps the request declared in its Pod template.

[#auto-ro-requirements]
== Requirements and scope

* *Cluster*: An EKS Auto Mode cluster running Kubernetes version 1.36 or later. {ro-short-cap} is available on every such cluster, including existing ones. You don't need to update the cluster or call an EKS API to use it.
* *Workloads*: Deployments and StatefulSets.
* *Resources*: CPU and memory. {ro-short-cap} doesn't size GPUs or ephemeral storage, and it doesn't change replica counts.
* *Namespaces*: {ro-short-cap} never manages workloads in the `kube-system`, `kube-public`, or `kube-node-lease` namespaces, even if a policy selects them.
* *Pricing*: {ro-short-cap} is available at no additional charge.
* *{aws} Regions*: US East (N. Virginia), US East (Ohio), US West (Oregon), Europe (Frankfurt), Europe (Ireland), Asia Pacific (Seoul), and Asia Pacific (Tokyo).

[#auto-ro-considerations]
== Preview considerations

Review these behaviors before you set `mode: Apply` on production workloads:

* *No automatic rollback*: If an applied recommendation degrades a workload, {ro-short} doesn't revert it. To stop further changes to that workload, opt it out or set its policy to `Recommend`. For instructions, see <<auto-ro-enable-opt-out>> and <<auto-ro-enable-pause>>.
* *Applied values stay in place*: Deleting a policy, switching to `Recommend`, or opting a workload out stops future changes only. Running Pods keep the CPU and memory that {ro-short} last applied. To return Pods to the values in the Pod template, restart the workload, for example with `kubectl rollout restart`. For StatefulSets that use the `OnDelete` update strategy, see <<auto-ro-enable-opt-out>>.
* *No cost or savings figures*: {ro-short-cap} doesn't report estimated savings in this preview. To measure the cost effect of rightsizing, use {aws} Cost Explorer or your existing cost tools.
* *Console access*: There is no {ro-short} page in the Amazon EKS console. The Kubernetes resource viewer shows `ClusterResourceOptimizationPolicy` and `ResourceOptimization` objects as read-only. For more information, see <<view-kubernetes-resources>>.
