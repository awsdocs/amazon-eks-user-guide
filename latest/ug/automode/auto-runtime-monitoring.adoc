= Monitor the EKS Auto Mode runtime
:info_titleabbrev: EKS Auto Runtime Monitoring

[abstract]
--
Collect logs and metrics from the components that run on EKS Auto Mode nodes.
--

Amazon EKS Auto Mode provides a streamlined experience for running Kubernetes on {aws}. It automatically provisions nodes by using {aws}-managed AMIs and Karpenter. EKS Auto Mode also runs a set of controllers in the control plane that aren't visible to you. To close the observability gap this can create, EKS delivers <<auto-managed-component-logs,{aws}-managed component logs>> for the control plane controllers. In addition, because the EKS Auto Mode runtime components are installed in the AMI and run on your nodes, you can configure your own log and metrics collectors to gather their logs and metrics.

This topic describes how to collect logs and metrics from the components that run on EKS Auto Mode nodes. For information about logs from the {aws}-managed controllers that run in the control plane, see <<auto-managed-component-logs>>.

== Runtime component logs

EKS Auto Mode removes the need for you to run critical add-ons such as CoreDNS, `kube-proxy`, and the Amazon VPC CNI. These add-ons are baked into the EKS Auto Mode AMIs and run as `systemd` services on your nodes. To collect logs from these components, use https://fluentbit.io/[Fluent Bit] through the link:AmazonCloudWatch/latest/monitoring/install-CloudWatch-Observability-EKS-addon.html[Amazon CloudWatch Observability add-on,type="documentation"], or the log aggregator of your choice.

Fluent Bit is configured with a `ConfigMap`. Within the configuration, you specify the `systemd` services you want to monitor by using `Systemd_Filter` entries in a `systemd` input. The following snippet illustrates the concept.

[source,yaml]
----
  dataplane-log.conf: |
    [INPUT]
      Name                systemd
      Tag                 dataplane.systemd.*
      Systemd_Filter      _SYSTEMD_UNIT=containerd.service
      Systemd_Filter      _SYSTEMD_UNIT=kubelet.service
      Systemd_Filter      _SYSTEMD_UNIT=coredns.service
      Systemd_Filter      _SYSTEMD_UNIT=kube-proxy.service
      Systemd_Filter      _SYSTEMD_UNIT=eks-ebs-csi-driver.service
      Systemd_Filter      _SYSTEMD_UNIT=eks-pod-identity-agent.service
      Systemd_Filter      _SYSTEMD_UNIT=eks-node-monitoring-agent.service
      DB                  /var/fluent-bit/state/systemd.db
      Path                /var/log/journal
      Read_From_Tail      ${READ_FROM_TAIL}
----

You can also collect file-based logs written by the VPC CNI components under `/var/log/aws-routed-eni/`. These include `ipamd`, `network-policy-agent`, `plugin`, and `ebpf-sdk` logs. To collect them, add a `tail` input to the configuration.

[NOTE]
====
The preceding example is shortened for clarity. For a complete `ConfigMap` that collects application, runtime, and host logs and ships them to CloudWatch Logs, see the Container Insights Fluent Bit configuration in the Amazon CloudWatch documentation.
====

== Runtime component metrics

Metric collection in EKS Auto Mode is similar to metric collection in self-managed EKS on Amazon EC2 nodes. The components that run on your nodes expose Prometheus metrics endpoints that you can collect with the scraper of your choice.

The following list shows the metrics endpoint (port and path) for each component.

CoreDNS:: `9153/metrics`
`kube-proxy`:: `10249/metrics`
IPAM daemon (`ipamd`):: `61678/metrics`
Network Policy Agent:: `8900/metrics`
Node Monitoring Agent:: `8801/metrics`
Pod Identity Agent:: `2705/metrics`

=== Querying a metrics endpoint

You can query an endpoint directly from a node to confirm that metrics are being served. The following example uses `curl` to read the CoreDNS metrics endpoint.

[source,bash]
----
curl localhost:9153/metrics
----

The output includes the Prometheus metrics exposed by the component.

[source,none]
----
# HELP coredns_build_info A metric with a constant '1' value labeled by version, revision, and goversion from which CoreDNS was built.
# TYPE coredns_build_info gauge
coredns_build_info{goversion="go1.26.3",revision="",version="1.13.2"} 1
# HELP coredns_cache_entries The number of elements in the cache.
# TYPE coredns_cache_entries gauge
...
----

To confirm which ports the node components are listening on, use `netstat`.

[source,bash]
----
netstat -tulpn | grep 127.0.0.1
----
