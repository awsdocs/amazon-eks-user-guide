[#ack-troubleshooting]
= Troubleshoot issues with ACK capabilities
:info_titleabbrev: Troubleshooting

[abstract]
--
Diagnose and resolve common issues with the EKS Capability for ACK.
--

[NOTE]
====
EKS Capabilities are fully managed and run outside your cluster.
You do not have direct access to controller namespaces.
You can configure controller log delivery for visibility into controller behavior.
See <<capabilities-controller-logs>>.
Troubleshooting focuses on capability health, resource status, and IAM configuration.
====

== Capability is ACTIVE but resources are not being created

If your ACK capability shows `ACTIVE` status but resources are not being created in {aws}, check the capability health, resource status, and IAM permissions.

*Check capability health*:

You can view capability health and status issues in the EKS console or using the {aws} CLI.

*Console*:

. Open the Amazon EKS console at https://console.aws.amazon.com/eks/home#/clusters.
. Select your cluster name.
. In the left navigation pane, choose *Cluster monitoring*.
. Choose the *Capabilities* tab to view health and status for all capabilities.

*{aws} CLI*:

[source,bash,subs="verbatim,attributes,quotes"]
----
# View capability status and health
aws eks describe-capability \
  --region [.replaceable]`region-code` \
  --cluster-name [.replaceable]`my-cluster` \
  --capability-name [.replaceable]`my-ack`

# Look for issues in the health section
----

*Common causes*:

* *IAM permissions missing*: The Capability Role lacks permissions for the {aws} service
* *Wrong namespace*: Resources created in namespace without proper IAMRoleSelector
* *Invalid resource spec*: Check resource status conditions for validation errors
* *API throttling*: {aws} API rate limits being hit
* *Admission webhooks*: Admission webhooks blocking the controller from patching resource status

*Check resource status*:

[source,bash,subs="verbatim,attributes,quotes"]
----
# Describe the resource to see conditions and events
kubectl describe bucket [.replaceable]`my-bucket` -n default

# Look for status conditions
kubectl get bucket [.replaceable]`my-bucket` -n default -o jsonpath='{.status.conditions}'

# View resource events
kubectl get events --field-selector involvedObject.name=[.replaceable]`my-bucket` -n default
----

*Verify IAM permissions*:

[source,bash,subs="verbatim,attributes,quotes"]
----
# View the Capability Role's policies
aws iam list-attached-role-policies --role-name [.replaceable]`my-ack-capability-role`
aws iam list-role-policies --role-name [.replaceable]`my-ack-capability-role`

# Get specific policy details
aws iam get-role-policy --role-name [.replaceable]`my-ack-capability-role` --policy-name [.replaceable]`policy-name`
----

== Resources created in {aws} but not showing in Kubernetes

ACK only tracks resources it creates through Kubernetes manifests.
To manage existing {aws} resources with ACK, use the adoption feature.

[source,yaml]
----
apiVersion: s3.services.k8s.aws/v1alpha1
kind: Bucket
metadata:
  name: existing-bucket
  annotations:
    services.k8s.aws/adoption-policy: "adopt-or-create"
spec:
  name: my-existing-bucket-name
----

For more on resource adoption, see <<ack-concepts>>.

== Cross-account resources not being created

If resources are not being created in a target {aws} account when using IAM Role Selectors, verify the trust relationship and IAMRoleSelector configuration.

*Verify trust relationship*:

[source,bash,subs="verbatim,attributes,quotes"]
----
# Check the trust policy in the target account role
aws iam get-role --role-name [.replaceable]`cross-account-ack-role` --query 'Role.AssumeRolePolicyDocument'
----

The trust policy must allow the source account's Capability Role to assume it.

*Confirm IAMRoleSelector configuration*:

[source,bash,subs="verbatim,attributes,quotes"]
----
# List IAMRoleSelectors (cluster-scoped)
kubectl get iamroleselector

# Describe specific selector
kubectl describe iamroleselector [.replaceable]`my-selector`
----

*Verify namespace alignment*:

IAMRoleSelectors are cluster-scoped resources but target specific namespaces.
Ensure your ACK resources are in a namespace that matches the IAMRoleSelector's namespace selector:

[source,bash,subs="verbatim,attributes,quotes"]
----
# Check resource namespace
kubectl get bucket [.replaceable]`my-cross-account-bucket` -n [.replaceable]`production`

# List all IAMRoleSelectors (cluster-scoped)
kubectl get iamroleselector

# Check which namespace the selector targets
kubectl get iamroleselector [.replaceable]`my-selector` -o jsonpath='{.spec.namespaceSelector}'
----

*Check IAMRoleSelected condition*:

Verify that the IAMRoleSelector was successfully matched to your resource by checking the `ACK.IAMRoleSelected` condition:

[source,bash,subs="verbatim,attributes,quotes"]
----
# Check if IAMRoleSelector was matched
kubectl get bucket [.replaceable]`my-cross-account-bucket` -n [.replaceable]`production` -o jsonpath='{.status.conditions[?(@.type=="ACK.IAMRoleSelected")]}'
----

If the condition is `False` or missing, the IAMRoleSelector's namespace selector does not match the resource's namespace.
Verify the selector's `namespaceSelector` matches your resource's namespace labels.

*Check Capability Role permissions*:

The Capability Role needs `sts:AssumeRole` and `sts:TagSession` permissions for the target account role:

[source,json,subs="verbatim,attributes,quotes"]
----
{
  "Version": "2012-10-17",{tcx5-waiver}
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["sts:AssumeRole", "sts:TagSession"],
      "Resource": [.replaceable]`"arn:aws:iam::444455556666:role/cross-account-ack-role"`
    }
  ]
}
----

For detailed cross-account configuration, see <<ack-permissions>>.

[#ack-stuck-deletion-disabled-service]
== Resource stuck in Terminating after a service was turned off

If you delete a Kubernetes resource whose ACK service is listed in the capability's `disabledServices`, the resource stays in the `Terminating` state and its {aws} resource is never deleted.
ACK adds a finalizer to every resource that it manages, named for the resource's group and kind, such as `finalizers.s3.services.k8s.aws/Bucket`.
The finalizer is removed only after a running controller deletes or releases the {aws} resource.
Because the controller for a turned-off service doesn't run, nothing removes the finalizer, and the `services.k8s.aws/deletion-policy` annotation isn't applied.

To confirm, check for a deletion timestamp and a remaining ACK finalizer:

[source,bash,subs="verbatim,attributes,quotes"]
----
kubectl get bucket [.replaceable]`my-bucket` -n [.replaceable]`my-namespace` \
  -o jsonpath='{.metadata.deletionTimestamp}{"\n"}{.metadata.finalizers}{"\n"}'
----

Then confirm that the service is turned off for the capability:

[source,bash,subs="verbatim,attributes,quotes"]
----
aws eks describe-capability \
  --region [.replaceable]`region-code` \
  --cluster-name [.replaceable]`my-cluster` \
  --capability-name [.replaceable]`my-ack` \
  --query 'capability.configuration.ack.disabledServices'
----

To resolve this, re-enable the service so that its controller runs and completes the deletion.
Remove the service from `disabledServices`, passing the complete list of services that you want to remain turned off.
If this service was the only one turned off, specify an empty list.
The following example re-enables `s3` while leaving `ec2` and `iam` turned off:

[source,bash,subs="verbatim,attributes,quotes"]
----
aws eks update-capability \
  --region [.replaceable]`region-code` \
  --cluster-name [.replaceable]`my-cluster` \
  --capability-name [.replaceable]`my-ack` \
  --configuration '{"ack": {"disabledServices": ["ec2", "iam"]}}'
----

After the capability returns to `ACTIVE`, the controller processes the pending deletion and removes the finalizer.

[WARNING]
====
Removing the finalizer by hand deletes the Kubernetes resource but leaves the {aws} resource in place, with no record of it in your cluster.
Only do this if you intend to keep the {aws} resource and manage it outside of ACK, or if you have already deleted it another way.

[source,bash,subs="verbatim,attributes,quotes"]
----
kubectl patch bucket [.replaceable]`my-bucket` -n [.replaceable]`my-namespace` \
  --type merge -p '{"metadata":{"finalizers":[]}}'
----

This clears every finalizer on the resource.
Confirm which finalizers are present before you run it, and be aware that clearing them also skips any cleanup that another controller's finalizer would have performed.
====

To avoid this, re-enable a service before you delete its resources, or delete the resources before you turn the service off.
For more information, see <<ack-configuration-options>>.
