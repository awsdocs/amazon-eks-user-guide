[.topic]
[#sandboxing-observability]
= Observability
:info_titleabbrev: Observability

[abstract]
--
Understand what you can observe for isolated and confidential pods that run in Nitro Sandboxes, and which node-level monitoring agents cannot see inside a sandbox.
--

Running a pod inside a Nitro Sandbox changes what you can observe and how. What you can see depends on the pod's mode, because the Cedar policy controls which operations the parent instance can perform.

[#sandboxing-observability-logs-exec]
== Logs and exec

`kubectl logs` works for sandboxed pods in both isolated and confidential mode. Container logs stream over the vsock channel to the parent instance.

`kubectl exec` (along with `stdin`, stats, and process listing) depends on the mode:

* *Isolated mode* permits `exec`, `stdin`, stats, and process listing, so interactive debugging works the same as for a standard pod.
* *Confidential mode* denies `exec`, `stdin`, stats, and process listing by default, so the parent instance cannot introspect the guest. You can permit specific exec commands when you generate the Cedar policy. For more information, see <<sandboxing-confidential-setup>>.

[#sandboxing-observability-agents]
== Node-level monitoring agents

Monitoring agents that run on the node cannot observe activity inside a Nitro Sandbox, because the sandbox isolates the pod from the node. This includes the Amazon CloudWatch Observability agent and the Amazon GuardDuty agent. Both continue to monitor standard pods and node-level activity on the same node. For more information, see <<cloudwatch>> and <<integration-guardduty>>.
