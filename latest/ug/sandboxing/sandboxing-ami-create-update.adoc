[#sandboxing-ami-create-update]
= Create and update a Nitro Sandbox AMI
:info_titleabbrev: Create and update

[abstract]
--
Build a custom AMI from the Nitro Sandbox binaries that {aws} publishes as a signed release, or use a supported AMI, and update it when {aws} publishes a new release.
--

EKS Auto Mode includes Nitro Sandbox support with no additional configuration. If you run managed node groups or self-managed nodes outside of Auto Mode, you need a compatible AMI. You have two options:

* *Use a supported AMI.* Nitro Sandbox supports Amazon Linux.
* *Build your own AMI* from the Nitro Sandbox binaries that {aws} publishes as a signed release.

The release delivers the runtime binaries and a host-kernel patch series. Each sandbox node runs two kernels: a *host kernel* and a pre-compiled *guest kernel* that boots inside every sandbox pod's microVM. On Amazon Linux, the host kernel already includes the required patches, so you do not apply the patch series or take any kernel action. On operating systems other than Amazon Linux, you build the host kernel from the patch series. You never build or modify the guest kernel. For how to download and verify the runtime binaries, see <<sandboxing-download-binaries>>.

[NOTE]
.Before you begin
====
Before you start, confirm you have an EKS cluster, a build instance with Nitro Enclaves enabled and Secure Boot disabled, and permissions to create AMIs, launch templates, and managed node groups. Each release ships OS-specific build guides and helper scripts for the supported operating systems.
====

[#sandboxing-ami-build]
== Build a custom AMI

The build follows these steps. On Amazon Linux, skip Step 2: the host kernel already includes the required patches, so no kernel action is needed. OS-specific differences are called out in the build guide included with the release.

[%header,cols="1,2,3"]
|===
|Step |Command |What it does

|1
|`scripts/verify-archives.sh`
|Unpack the runtime binaries archive and the host-kernel patch series archive, and validate every shipped checksum.

|2
|`scripts/build-kernel-<os>.sh <patch-dir>`
|On operating systems other than Amazon Linux, build the host kernel with the patch series, install it, and reboot into it. Amazon Linux already includes these patches, so you skip this step.

|3
|`scripts/install-runtime.sh <bundle-dir>`
|Install the runtime binaries, stage the guest image, and write the shim config.

|4
|By hand (per the OS guide)
|Wire the containerd runtime handlers and the kubelet endpoint, then bake the AMI and join the cluster.
|===

After building, apply the `isolated-sandbox` and `confidential-sandbox` `RuntimeClass` objects once per cluster, each with a scheduling `nodeSelector` that matches the node labels set at join time. Pods that set `runtimeClassName: isolated-sandbox` or `runtimeClassName: confidential-sandbox` then schedule onto those nodes. For the full procedure, see the build guide in the bundle.

[#sandboxing-ami-update]
== Update an AMI

When {aws} publishes a new release, rebuild your AMI. Each release is versioned, and a newer version replaces the previous one. The release notes list which components changed and whether a kernel rebuild is required.

[%header,cols="2,3,2,1"]
|===
|Category |What changed |Steps to repeat |Reboot

|Runtime update
|New binaries or guest image, same kernel patches
|Steps 1 and 3
|No

|Kernel update
|New or updated patch series
|Steps 1, 2, and 3
|Yes

|Full bundle update
|Both kernel patches and runtime
|All four steps
|Yes
|===

Launch a fresh build instance from your current sandbox AMI so the update applies only the changed components, then repeat the steps for the update category and bake a new AMI. Update your launch template to the new AMI and roll out the managed node group one node at a time.

[IMPORTANT]
.Update Cedar policies when the guest image changes
====
When the guest image changes, PCR0 changes, and existing Cedar policies for confidential pods no longer match. Before rolling out, regenerate the Cedar policies with the new bundle's `eks-nitro-sandbox-genpolicy` and update any KMS key policy conditions that reference the old PCR0 value. Nodes on the old AMI keep serving existing confidential workloads until you drain them. For more information, see <<sandboxing-confidential-setup>>.
====

Tag each AMI with the bundle identifier (for example, `nitro-sandbox-ga-20260929-r2`) so you can track which bundle version each node group runs.
